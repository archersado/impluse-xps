# 原始问题

用户要求先定义清楚 XPS 的产品理念：围绕一个场景构建 Agent 协作网络，Agent 是核心执行主体；人负责确权、责任、决策／批准和策略设计；Lab 涌现中心圈定一组 Agent 产出方案，在沙盒中与参照组执行比对，推动场景业务效果进化（S-033～S-035）。

# 问题定义

- 期望状态：产品理念能同时解释场景协作网络、人机分工、运行节拍及 Lab 的实验进化，并指导后续产品形态讨论。
- 当前状态：已有价值流、节拍、工作项、授权、瓶颈处置等局部决策（Q-20261010-001），尚未有统领它们的场景网络与 Lab 理念。
- 核心差距：局部功能尚未连成“Agent 主导执行、人在治理、实验驱动演进”的整体产品逻辑。
- 影响与边界：本轮定义产品理念；具体界面、Agent 编排方式、沙盒技术和实验统计方法待后续讨论。
- 成功判据：能够用一段清晰定义及两条运行闭环解释既有设计，且标出尚未确认的权责与实验推广门禁。

# 问题分解

## 静态结构

- 场景、业务目标、价值流、Agent 协作网络、工作项、人类治理角色、Lab、沙盒与参照组。

## 动态过程

- 生产运行：Agent 网络执行工作项，识别瓶颈与风险，在授权内协同和处置；人在责任、策略与决策节点确权。
- 进化实验：圈定 Agent 组生成候选方案，在沙盒与参照组比对业务结果，决定是否调整生产网络或策略；最终推广门禁待确认。

## 因果与假设

- inferred：Lab 的对照实验若使用同一场景业务效果指标，有助于区分方案改善与自然波动；实验设计与可比性尚需验证。
- inferred：生产运行与实验进化共享场景模型，才便于比较并把结果反馈给运行策略；用户尚未确认具体共用边界。

## 优先级

- 高：先收敛产品理念，再讨论 Lab 具体产品形态。

# Discussion

## Round 1 — 2026-10-15

- 观点：用户重申 XPS 的核心是围绕场景构建 Agent 协作网络，Agent 为核心执行主体，人负责确权、责任、决策／批准与策略设计；Lab 用多 Agent 方案涌现和沙盒参照组比对驱动业务效果进化。
- 证据：S-033～S-035。
- 反例或冲突：此前讨论偏重节拍和瓶颈处置，容易把平台缩成协调功能；Lab 尚未说明方案类型、对照条件和推广权限。
- 暂定结论：以“场景 Agent 协作网络”为产品主体，以“运行协调”和“实验进化”为两个核心闭环；这后一层组织方式是对用户陈述的产品化归纳，待确认。
- 未解项：人类对 Lab 实验方案进入生产的批准权；涌现方案可改变的对象；业务效果评价口径；沙盒与实际场景的映射。

## Round 2 — 2026-10-15

- 观点：用户确认 Lab 成果进入正式协作网络的分级批准：单场景 Agent 组合或策略变更由价值流负责人批准；跨场景语义或企业级规则变更由对应企业级责任人批准。
- 证据：S-043；组织语义责任人见 S-041。
- 反例或冲突：实验效果较好不自动赋予修改生产策略、企业规则或共用语义的权限；混合影响的实验需分别走对应批准链。
- 暂定结论：Lab 产出可验证候选方案及对照证据，按影响范围交有权的人批准后进入生产；实验和正式运行的状态必须区分。
- 未解项：效果阈值、混合影响拆分、灰度与回滚、参照组可比性、实验数据隔离。

## Round 3 — 2026-10-15

- 观点：用户收束当前产品范围，面向场景价值流的构建，暂不考虑跨场景事项；并未限定只能有一条场景价值流。
- 证据：S-044。
- 反例或冲突：上一轮讨论了跨场景语义及企业级规则的推广门禁；该规则可保留为后续阶段治理原则，但不能成为当前阶段产品交付要求。
- 暂定结论：当前阶段以每条场景价值流为独立构建单元；Agent 运行节拍与同场景 Lab 对照保留为产品理念，是否本阶段交付待确认。跨场景共享、推广与组织级演进后置。
- 未解项：场景与价值流是否一对一、价值流构建完成判据、运行与 Lab 是否纳入本阶段及其最小验证范围。

## Round 4 — 2026-10-15

- 观点：用户要求构建的场景价值流和 Agent 网络在一个实际工作项上跑通并验证。
- 证据：S-045。
- 反例或冲突：只完成配置而没有实际执行证据不足以证明场景可运行；单个工作项跑通也不足以证明长期周期与可预测性改善。
- 暂定结论：本阶段交付包括场景价值流构建与一个真实工作项的端到端试运行／验收证据；Lab 对照实验是否进入本阶段仍未确定。
- 未解项：试点场景与工作项、真实工作项的敏感数据边界、执行与人工批准节点、完成事件和验收者、效果评价的最低证据。

## Round 5 — 2026-10-15

- 观点：用户认可由平台 Agent 引导价值流负责人选择真实试点工作项，使试点覆盖 Agent 实际执行、必要的人类决策与最终验收证据。
- 证据：S-046。
- 反例或冲突：若试点只有流程模拟或只有人工操作，无法验证 Agent 网络；若工作项恰无必要人工决策，不应为了测试而制造审批节点，具体适配待定义。
- 暂定结论：试点选择是价值流构建功能的一部分，Agent 提示验证覆盖项，负责人选定实际工作项；执行后检查所需节点是否留下证据。
- 未解项：试点代表性标准、数据权限准备、失败后调整场景模型的方式，以及无人工决策路径如何验证授权边界。

## Round 6 — 2026-10-15

- 观点：用户确认场景构建从可验收的业务结果和完成事件开始，再由 Agent 梳理工作项、参与者、知识／数据／能力与授权，最后以真实工作项跑通验证。
- 证据：S-047。
- 反例或冲突：若先配置 Agent 和工具而未明确业务结果，后续验收缺乏判断依据；结果虽明确但未定义可观察完成事件，也无法关闭工作项。
- 暂定结论：以结果和完成事件为构建入口，逐步生成价值流与 Agent 协作网络，并以真实工作项形成验证闭环。
- 未解项：构建过程是否允许从现有流程导入作为辅助证据、每一步谁确认、失败试运行如何回修模型。

## Round 7 — 2026-10-15

- 观点：用户同意平台 Agent 根据价值流生成 Agent 分工与协作关系初稿，价值流负责人修正并为 Agent 确认权限。
- 证据：S-048。
- 反例或冲突：自动生成网络初稿不代表 Agent 能自授执行权；未经负责人确权的网络只能作为待确认方案。
- 暂定结论：场景价值流模型驱动 Agent 网络草案生成；负责人确认分工、协作关系及权限后，网络才可承载真实工作项。
- 未解项：Agent 角色推导依据、何时复用既有 Agent、人与 Agent 的交接如何表达、网络变更版本与撤回。

## Round 8 — 2026-10-15

- 观点：用户要求现有 Agent 无法覆盖某环节能力时，平台 Agent 生成新 Agent 候选定义，包含所需知识、数据、能力与权限，由价值流负责人确认。
- 证据：S-049。
- 反例或冲突：候选定义与可实际执行的 Agent 仍有差距；负责人确认职责与权限不代表新 Agent 的能力已通过验证。
- 暂定结论：网络构建需显露能力缺口，并提供“复用／配置现有 Agent”与“生成新 Agent 候选”的路径；新候选先经负责人确权，执行可靠性验证方式待定。
- 未解项：缺口判定、Agent 候选的生成与验证、启用门禁、与现有 Agent 的职责重叠处理。

## Round 9 — 2026-10-15

- 观点：用户认可新 Agent 候选在负责人确权后，先用场景内样例任务检验目标环节能力、数据使用和授权边界，通过后再进入真实工作项。
- 证据：S-050。
- 反例或冲突：负责人确权只能说明可授权的职责，不能直接证明候选 Agent 已具备稳定执行能力；样例任务通过也不等于业务效果已由 Lab 对照实验验证。
- 暂定结论：候选定义 → 负责人确权 → 场景内样例任务验证 → 启用 → 真实工作项验证；样例验证属于当前场景构建门禁，Lab 效果对照仍单独规划。
- 未解项：样例如何生成、能力与授权检查的通过条件、失败后如何回修候选、验证结果是否有有效期。

## Round 10 — 2026-10-15

- 观点：用户要求真实工作项未通过验收时，平台 Agent 依据执行证据定位价值流模型、Agent 能力、数据或授权问题，生成修订草案，经价值流负责人确认后重试。
- 证据：S-051。
- 反例或冲突：失败归因可能涉及多个原因，Agent 的诊断应保留不确定性与证据；重试不应覆盖原试点记录。
- 暂定结论：试点验收失败进入“证据诊断 → 修订草案 → 负责人确认 → 新版本重验”的构建回路，版本与试验记录可追溯。
- 未解项：失败分类依据、何时由负责人拒绝修订、最大重试或人工接管条件、如何判定回修后通过。

## Round 11 — 2026-10-15

- 观点：用户认同场景价值流蓝图固定业务里程碑、验收门和授权规则，而每个真实工作项由 Agent 按具体情况动态拆解任务、安排协作。
- 证据：S-052。
- 反例或冲突：动态任务计划若改变已确认的验收门或超出授权，就不再只是工作项内部调度；须显露并交有权人处理，具体门禁待定义。
- 暂定结论：区分相对稳定的场景蓝图与逐项生成的运行计划；两者共同支撑可预测的交付节奏与 Agent 灵活执行。
- 未解项：验收门的配置粒度、动态计划的留痕、哪些偏离需要负责人确认。

## Round 12 — 2026-10-15

- 观点：用户确认 Agent 可在验收门证据明确、可核验且处于预授权范围内时直接放行；需要人的判断、证据不足或超出授权时交有权的人决策。
- 证据：S-053。
- 反例或冲突：有证据不等于证据充分；自动放行必须同时满足该门的判定标准与有效授权，不能以 Agent 自评取代人的必要判断。
- 暂定结论：每个验收门须定义证据要求、可自动判定范围及超出范围的决策责任人；Agent 执行时按证据与授权决定放行或提交决策。
- 未解项：证据充分标准、证据来源及可信度、最终验收是否适用自动放行、异常升级细节。

## Round 13 — 2026-10-15

- 观点：用户认可证据暂时不足时，由 Agent 在授权内先从连接系统或协作 Agent 补证，并结合承诺剩余时间及失约风险及时升级；需要人的专业判断时直接交人。
- 证据：S-054。
- 反例或冲突：补证不能无限等待，也不能借协作 Agent 绕过数据或能力授权；专业判断不能伪装为补证自动放行。
- 暂定结论：验收门有“待补证”运行状态，Agent 可主动补证与动态升级；放行仍受 S-053 的证据和授权双条件限制。
- 未解项：补证上限、证据可信度、提前升级阈值、无交付承诺时的时效依据。

## Round 14 — 2026-10-15

- 观点：用户澄清最终业务结果若涉及定性目标（非定量目标），需由人验收确认。
- 证据：S-055。
- 反例或冲突：可量化指标达标不能代替同一业务结果中的定性目标判断；纯定量结果也不能仅因可量化就跳过证据与授权条件。
- 暂定结论：业务结果验收应显式区分定性与定量判定条件；含定性目标的最终验收由指定的人确认。纯定量结果是否可自动验收仍待明确。
- 未解项：混合目标的验收组合方式、人的确认对象、纯定量自动验收的适用条件。

## Round 15 — 2026-10-15

- 观点：用户认可纯定量业务结果在证据可核验且预授权有效时由 Agent 自动验收；不满足条件时交有权的人。
- 证据：S-056；含定性目标由人确认见 S-055。
- 反例或冲突：目标以数字表达不代表测量口径可信，也不自动授予 Agent 验收权。
- 暂定结论：最终业务结果验收按目标性质、证据可核验性和有效授权判定；含定性目标由人确认，纯定量且满足双条件时可自动完成。
- 未解项：量化口径和数据源确认、证据时效、混合目标中的定量部分如何呈现给验收人。

## Round 16 — 2026-10-15

- 观点：用户指出网络有三个维度：业务价值流表达目标、价值流动关系与承载点；围绕价值流建立 Agent 与人的协作网络以保障交付；执行维度按具体工作项拆解、分派和执行任务，主体可以是人或 Agent。
- 证据：S-057。
- 反例或冲突：上一轮助手把协作网络节点直接定义为“职责单元”，混淆了业务价值承载点、协作主体与运行任务，也弱化了人在网络中的执行作用。
- 暂定结论：分别建模业务价值流、Agent／人协作网络和任务执行，并建立它们的关联。具体节点类型、映射基数与变更边界仍需讨论。
- 未解项：一个价值承载点如何关联多个协作主体；一个 Agent／人能否参与多个承载点；任务在动态重分派时如何保持目标、授权和证据关联。

## Round 17 — 2026-10-15

- 观点：用户确认场景级 Agent／人协作网络是负责人确认的可复用结构；具体工作项可动态选择参与者、拆解及转派任务；长期改变协作结构需要负责人确认新版本。
- 证据：S-058。
- 反例或冲突：工作项内的临时转派不应无声改写所有后续工作项的网络；场景级网络版本也不应锁死对当下瓶颈的授权内调整。
- 暂定结论：协作网络保留场景版本，具体工作项保留运行计划与转派记录；长期结构变更经负责人确认后生效。
- 未解项：网络可表达的关系类型、临时调整何时升级为长期变更、版本生效及已运行工作项的处理。

## Round 18 — 2026-10-15

- 观点：用户明确价值流中的价值承载点是业务成果与业务状态。
- 证据：S-059。
- 反例或冲突：参与者、职责或临时执行任务本身不能直接代替价值承载点；它们与成果／状态关联。
- 暂定结论：价值流以业务成果与状态作为核心节点；这些节点间如何表达推进、分支、返工及验收，继续讨论。
- 未解项：成果与状态的区分、节点粒度、边的语义、证据要求和版本影响。

## Round 19 — 2026-10-15

- 观点：用户认可业务价值状态与工作项运行状态分开；等待、阻塞、失约风险投影到价值流，用以观察瓶颈。
- 证据：S-060。
- 反例或冲突：把“等待审批”设为价值承载点会混淆价值形成与运行停滞；仅看已完成的业务状态则无法感知等待风险。
- 暂定结论：价值流保存业务成果／状态，工作项保存等待、阻塞和风险等运行状态；平台把运行状态关联到当前价值承载点进行节拍协调。
- 未解项：投影关系、等待起止事件、并行任务的停滞归因、风险触发阈值。

## Round 20 — 2026-10-15

- 观点：用户要求 AI 节拍与场景协作支持 Supervisor 模式和群体协调模式两种形态。
- 证据：S-061。
- 反例或冲突：将场景协调固定为单一 Supervisor Agent 会排除群体协调；将群体协调理解为无统一授权或冲突裁决也与既有治理规则冲突。
- 暂定结论：两种模式都应能作用于同一场景价值流与工作项模型；协调职责的分配可不同，授权、风险呈现、证据和有权人的决策边界保持可检查。
- 未解项：默认模式由谁设置、运行时是否可切换、群体协调如何形成最终行动决议、模式切换如何影响进行中的工作项。

## Round 21 — 2026-10-15

- 观点：用户同意场景设默认协调模式，并允许具体价值承载点选用另一模式，因此同一场景可组合 Supervisor 和群体协调。
- 证据：S-062。
- 反例或冲突：场景统一模式不足以表达不同价值承载点的协作需要；承载点模式覆盖也不能使工作项跨点推进时丢失责任与证据。
- 暂定结论：协调模式配置具有场景默认值和价值承载点覆盖值；生效模式随工作项当前承载点确定，跨模式交接细节待定。
- 未解项：覆盖规则、模式配置确认者、群体协调决议方式、进行中切换和跨模式交接。

## Round 22 — 2026-10-15

- 观点：用户认可群体协调中由任一有权限的 Agent 基于瓶颈或风险提案，受影响的 Agent 与人反馈能力、责任和风险；规则内无冲突的动作直接执行，有冲突则由 Agent 协商、决策管理员确认。
- 证据：S-063；此前冲突确认规则见 S-007～S-010。
- 反例或冲突：有发起权不等于有越过他人责任或授权直接改派的权力；群体协调也不意味着所有参与者均须投票。
- 暂定结论：群体协调通过授权提案、受影响方反馈、规则检查和冲突确认形成可执行动作；决策管理员只处理需确认的冲突方案。
- 未解项：受影响方范围、响应时限、协商失败和未响应时的升级、最终执行动作归属。

## Round 23 — 2026-10-15

- 观点：用户认可 Supervisor 模式中各 Agent 可报告瓶颈、风险与建议，由 Supervisor Agent 汇总并在预授权内选择／下达调度动作；受影响方可提出冲突，冲突方案仍由决策管理员确认。
- 证据：S-064。
- 反例或冲突：Supervisor 集中调度不能替代有权人的冲突确认，也不意味着其他 Agent 只能被动执行、不能报告问题。
- 暂定结论：两模式共享授权、风险与冲突治理，区别在协调动作的发起及形成路径：Supervisor 汇总选择，群体模式允许任一有权限 Agent 提案并汇聚受影响方反馈。
- 未解项：两种模式的动作日志结构、Supervisor 无响应时的接管、模式切换过程中未完成提案的处理。

## Round 24 — 2026-10-15

- 观点：用户确认同一工作项可并行推进多个业务成果／状态。
- 证据：S-065。
- 反例或冲突：将工作项压成唯一“当前业务状态”会丢失并行推进与分别验收的事实。
- 暂定结论：价值流支持并行路径；工作项可同时关联多个正在推进的业务成果／状态，并分别记录其任务、证据和运行状态。
- 未解项：并行分支汇合门禁、部分完成、跨分支优先级和对最终交付风险的贡献。

## Round 25 — 2026-10-15

- 观点：用户同意并行成果的汇合条件由场景蓝图定义，区分必备、条件择一和可豁免成果；Agent 动态安排分支任务，但改变汇合条件要价值流负责人确认。
- 证据：S-066。
- 反例或冲突：任务调度权不能扩展为降低业务验收要求；条件豁免需要依据和有权确认，不能成为无痕跳过分支。
- 暂定结论：汇合门是价值流蓝图中的稳定业务约束，工作项运行动态执行但不得自行改写；临时修订需负责人确认并保留证据。
- 未解项：汇合条件的表达、豁免证据、运行中蓝图修订对已有工作项的影响、跨分支瓶颈识别。

## Round 26 — 2026-10-15

- 观点：用户认可由平台 Agent 对话引导价值流负责人构建场景，同时生成可直接编辑的价值流图和协作网络图；真实工作项运行后展示任务、风险与证据。
- 证据：S-067。
- 反例或冲突：对话生成和图上修改若各自形成不同版本，会导致负责人确认的蓝图与 Agent 执行依据不一致。
- 暂定结论：场景构建工作台需让对话与两张图指向同一场景草案；负责人可直接修订并确认，运行视图关联该版本。
- 未解项：对话／图编辑同步、差异解释、确认粒度、版本生效与工作台布局。

## Round 27 — 2026-10-15

- 观点：用户认为交付物交接、共同协作、授权与决策、替补与升级四类关系基本涵盖协作网络图的核心关系。
- 证据：S-068。
- 反例或冲突：“基本涵盖”不能解释为关系集合封闭；状态／风险反馈等信息流可能无法由四类关系充分表达。
- 暂定结论：首版以四类为核心候选，并继续检查是否需要独立的观察、通知或反馈关系。
- 未解项：状态与风险信息流、知识／数据共享关系是否属于协作图，关系方向与权限粒度。

## Round 28 — 2026-10-15

- 观点：用户认同将状态／风险观察和反馈作为协作网络关系，并要求 Agent 自身能够接收外部通知消息。
- 证据：S-069。
- 反例或冲突：仅靠交接或审批关系无法表达“需要知道、尚不需行动”的信号；收到通知也不自动意味着获得执行权限。
- 暂定结论：协作网络包含独立的信息观察／反馈关系，Agent 有外部消息接收入口；消息关联、可信度和动作选择继续设计。
- 未解项：通知来源、定向／订阅模式、去重时效、消息与工作项映射、何种消息可触发授权内动作。

## Round 29 — 2026-10-15

- 观点：用户确认外部通知既支持指定 Agent 定向投递，也支持按场景事件类型订阅；Agent 需确认来源和关联工作项，按既有授权决定是否行动，通知本身不产生执行权。
- 证据：S-070。
- 反例或冲突：通知可唤起 Agent 的判断，但发送方不能借通知绕过价值流负责人确权或既有策略门禁。
- 暂定结论：外部通知是 Agent 运行输入；定向与订阅共存，收到后先关联上下文，再依知识／数据／能力、策略和授权选择动作。
- 未解项：来源可信度、订阅权限、无关联工作项时如何处理、重复或过期通知、事件追溯。

## Round 30 — 2026-10-15

- 观点：用户确认 Agent 可从无法关联现有工作项的外部通知中自动受理新工作项，前提是来源可信、归属已配置场景且符合预设规则；不明确则交价值流负责人判断并保留通知。
- 证据：S-071。
- 反例或冲突：收到新通知不代表每条都应创建工作项；重复消息、场景不明和未获授权的来源需避免自动进入生产流。
- 暂定结论：外部通知进入后先尝试关联已有工作项；无匹配时按受理规则自动创建或交负责人判断；原消息与判定依据可追溯。
- 未解项：去重、可信来源登记、受理规则配置、创建后初始状态与承诺形成关系。

## Round 31 — 2026-10-15

- 观点：用户认可自动建项后 Agent 可立即在授权内准备和执行；完成时间仍是预测，只有价值流负责人确认后才形成对客户的交付承诺。
- 证据：S-072；此前预测／承诺边界见 S-016。
- 反例或冲突：自动建项不代表对客户承诺交付日期；缺少承诺也不应阻止已有授权覆盖的内部准备与执行。
- 暂定结论：建项、执行启动与对外承诺是可分别发生并留痕的动作；预测可供负责人评估后确认承诺。
- 未解项：承诺前执行范围、预测刷新与承诺冲突、对外沟通时点和撤销工作项规则。

## Round 32 — 2026-10-15

- 观点：用户确认 AI 节拍应在并行价值流中识别制约汇合门和最终验收的分支，综合承诺剩余时间、失约风险及质量、成本、合规风险协调，而非仅看等待时长。
- 证据：S-073。
- 反例或冲突：等待最长的分支若仍有余量，可能不是当前瓶颈；短等待但逼近汇合期限的分支可能更应优先处置。
- 暂定结论：节拍判断以汇合影响和多风险为依据，决定何时调度、替补或升级；具体预测与权衡机制尚需验证。
- 未解项：分支预计完成时间、关键分支变化、风险偏好、处置动作对其他分支承诺的影响。

## Round 33 — 2026-10-15

- 观点：用户认可首个真实工作项试点必须包含并行成果与汇合门，且至少留下 Agent 一次分支风险判断和协调选择记录，可包括有依据的暂不干预。
- 证据：S-074。
- 反例或冲突：只跑通任务和最终验收无法验证 AI 节拍判断链；单项试点也不能证明长期周期或可预测性改善。
- 暂定结论：试点选择标准在 Agent 执行、必要人工决策、最终验收基础上，增加并行汇合和一次可追溯节拍判断；绩效改进另待多样本验证。
- 未解项：候选工作项如何保证代表性、判断记录必备字段、真实风险未出现时的观察标准。

## Round 34 — 2026-10-15

- 观点：用户选择首个真实工作项先跑通一种协调模式。
- 证据：S-075。
- 反例或冲突：此前确认同一场景支持 Supervisor 与群体协调以及承载点模式覆盖（S-061、S-062），不等于首个试点必须同时验证两种模式和交接。
- 暂定结论：首个试点保持并行汇合、节拍判断与真实验收要求，但只要求一种协调模式跑通；另一模式及跨模式交接的验证时点待定。
- 未解项：试点首选模式、另一模式的场景样例或后续真实项验证方案、跨模式交接验收标准。

## Round 35 — 2026-10-15

- 观点：用户选择首个真实工作项采用 Supervisor 模式。
- 证据：S-076。
- 反例或冲突：首个试点选择 Supervisor 不取消平台对群体协调模式的产品要求（S-061）；也不能据此声称已验证跨模式交接。
- 暂定结论：试点以一个 Supervisor 协调 Agent 汇总并在预授权内下达动作，配合并行汇合、风险判断与最终验收，验证核心运行链。
- 未解项：Supervisor Agent 选型／生成、预授权、试点场景和工作项、群体模式后续验证时点。

## Round 36 — 2026-10-15

- 观点：用户确认节拍决策记录是工作项核心对象，记录汇合门、剩余承诺时间、分支预测与风险、可选动作、Supervisor 选择及授权、执行后结果；暂不干预也要留理由。
- 证据：S-077。
- 反例或冲突：只记录最终动作无法复盘当时为什么选择，也无法区分正确不干预与漏报；只记录预测不回看结果无法验证节拍有效性。
- 暂定结论：每次关键协调形成可追溯的决策记录，作为首个试点 AI 节拍判断的主要验收证据。
- 未解项：记录自动生成触发、预测快照、结果回看频率、修订与审计边界。

# 方案

- 产品理念讨论稿：[product-philosophy.md](../product-philosophy.md)。
- 首阶段功能清单与场景工作台流程讨论稿：[first-phase-features-and-workbench.md](../first-phase-features-and-workbench.md)。
- 已确认的推广门禁：单场景变更由价值流负责人批准，跨场景语义／企业级规则变更由对应企业级责任人批准（S-043）。
- 当前阶段聚焦按场景价值流独立构建，并用一个真实工作项试运行验证（S-044、S-045）；Lab 场景内比对保留为理念，交付时点待确认；跨场景门禁仅作后续原则。
- 已确认的试点选择：平台 Agent 引导价值流负责人选择能覆盖 Agent 执行、必要人工决策及验收证据的真实工作项（S-046）。
- 已确认的构建顺序：业务结果与完成事件 → 工作项／参与者 → 知识、数据、能力与授权 → 真实工作项验证（S-047）。
- 已确认的网络构建：平台 Agent 根据价值流生成分工与协作关系草案，价值流负责人修正并确权（S-048）。
- 已确认的缺口补齐：现有 Agent 不足时生成新 Agent 候选，列明知识、数据、能力和权限，由负责人确认（S-049）。
- 已确认的启用门禁：新 Agent 候选确权后须经场景内样例任务验证能力、数据使用与权限边界，合格后才进入真实工作项（S-050）。
- 已确认的失败回修：真实试点未通过验收时，Agent 诊断模型／能力／数据／授权问题，负责人确认修订后重验（S-051）。
- 已确认的蓝图边界：固定业务里程碑、验收门和授权规则；具体工作项由 Agent 动态拆解任务并安排协作（S-052）。
- 已确认的门禁原则：可核验证据与预授权同时满足时 Agent 可放行；需人判断、证据不足或超授权时交有权人决策（S-053）。
- 已确认的补证路径：暂缺证据时 Agent 先在授权内主动补证，按承诺剩余时间与失约风险及时升级；需人专业判断时直接交人（S-054）。
- 已确认的最终验收边界：业务结果含定性目标时须由人验收确认（S-055）。
- 已确认的纯定量自动验收：证据可核验且预授权有效时 Agent 可验收，否则交有权的人（S-056）。
- 已确认的三维模型：业务价值流、Agent 与人协作网络、工作项任务执行分别表达目标价值流动、保障交付的主体协作、具体任务拆分与执行（S-057）。
- 已确认的版本边界：场景级协作网络经负责人确认并复用；工作项内动态选择、拆解和转派；长期网络变更再由负责人确认新版本（S-058）。
- 已确认的价值承载点：业务成果与状态（S-059）。
- 已确认的状态分层：业务价值状态属价值流；等待／阻塞／失约风险属工作项运行状态，并投影价值流观察瓶颈（S-060）。
- 已确认的协调形态：场景内支持 Supervisor 模式和群体协调模式（S-061）。
- 已确认的模式粒度：场景默认模式与价值承载点覆盖模式可共存（S-062）。
- 已确认的群体协调：有权限 Agent 可提案，受影响方反馈；规则内无冲突直接执行，有冲突经 Agent 协商及决策管理员确认（S-063）。
- 已确认的 Supervisor 协调：各 Agent 报告建议，Supervisor 在预授权内汇总选择并下达动作；冲突仍交决策管理员确认（S-064）。
- 已确认的价值流并行：同一工作项可并行推进多个业务成果／状态（S-065）。
- 已确认的并行汇合门：必备、条件择一和可豁免成果由蓝图定义；改动须负责人确认（S-066）。
- 已确认的构建入口：平台 Agent 对话引导、生成可编辑价值流与协作网络图，运行时展示任务／风险／证据（S-067）。
- 初步认可的协作关系：交付物交接、共同协作、授权与决策、替补与升级四类基本涵盖，集合未封闭（S-068）。
- 已确认的信息关系与能力：观察／反馈作为协作关系，Agent 能接收外部通知消息（S-069）。
- 已确认的通知运行：定向投递与事件订阅并存；来源／工作项校验后按已有授权行动，通知不授予执行权（S-070）。
- 已确认的新工作项受理：可信且场景／规则匹配时 Agent 可由外部通知创建工作项，否则交负责人并保留通知（S-071）。
- 已确认的建项后运行：Agent 可立即在授权内准备／执行；预测经负责人确认才形成客户承诺（S-072）。
- 已确认的节拍判断：优先识别制约汇合门／最终验收的分支，综合承诺剩余时间和交付／质量／成本／合规风险（S-073）。
- 已确认的首个试点验证：包含并行汇合及至少一次有证据的分支风险判断和协调选择（S-074）。
- 已确认的首个试点模式范围：先跑通一种协调模式，两种模式交接不作为该工作项必需验证项（S-075）。
- 已确认的首个试点模式：Supervisor（S-076）。
- 已确认的节拍决策记录：关联工作项并保留当时输入、可选动作、选择／授权及后续结果（S-077）。
- 完整方案与验证计划：pending。
